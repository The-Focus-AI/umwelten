# MCP 2026-07-28: The Stateless Revision — Deep Dive and Umwelten Impact Map

*Date: 2026-07-29 | Spec: [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28) (supersedes 2025-11-25)*

---

## Overview

The 2026-07-28 revision is the largest re-architecture of MCP since Streamable HTTP. Its
organizing idea is **statelessness all the way down**: no protocol sessions, no handshake, no
server-initiated requests, no resumable streams. Every request is self-describing; every piece
of cross-call state becomes an explicit, server-minted handle that travels as data. The features
that assumed a long-lived bidirectional channel — Roots, Sampling, Logging — are deprecated
outright, and the interactive pieces (elicitation, sampling when you still want it, roots) are
re-expressed as a request/retry pattern called **Multi Round-Trip Requests (MRTR)**.

For umwelten this lands unusually well: our servers were already built stateless per request
(`sessionIdGenerator: undefined` everywhere), our A2A layer already owns session identity, and we
never implemented Roots/Sampling/Logging. The two real migration fronts are **OAuth client
registration** (we implement the now-deprecated Dynamic Client Registration on *both* the client
and the authorization-server side) and the **legacy `2024-11-05` client stack**, which is now
three revisions of dead weight. The two real opportunity fronts are **MRTR-shaped elicitation**
(a UX surface we've never had) and the **tasks extension**, which is a near-clone of the A2A task
polling model we standardized in ADR 0007.

## Part 1 — What actually changed

### 1.1 Stateless core: sessions, initialize, and discovery

- **`Mcp-Session-Id` is gone.** List endpoints must not vary per-connection. Servers that need
  cross-call state mint explicit handles and pass them as ordinary tool arguments (SEP-2567).
- **`initialize` / `notifications/initialized` are gone.** Every request now carries its protocol
  version and client capabilities in `_meta`:
  `io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`,
  `io.modelcontextprotocol/clientInfo`; servers answer with
  `io.modelcontextprotocol/serverInfo` in each result's `_meta` (SEP-2575).
- **`server/discover` is a new mandatory RPC** — servers MUST implement it. It returns
  `supportedVersions`, capabilities (including extensions), and identity, and doubles as a
  back-compat probe. It replaces initialize as the discovery step, and its result is cacheable
  (`ttlMs`/`cacheScope`).
- **SSE resumability is gone.** No `Last-Event-ID`, no event IDs. A broken response stream loses
  the in-flight request; clients re-issue with a new request id.
- **The GET stream and `resources/subscribe` are replaced by `subscriptions/listen`** — one
  long-lived POST-response stream carrying only the notification types the client opted into
  (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions`).
  Request-scoped notifications (`notifications/progress`, `notifications/message`) stay on the
  originating request's response stream.
- **`ping`, `logging/setLevel`, `notifications/roots/list_changed` removed.** Log level is now
  per-request via `_meta` `io.modelcontextprotocol/logLevel`.

### 1.2 MRTR: server-initiated requests become retries

This is the breaking change with the deepest design consequences. Servers may no longer *send*
`elicitation/create`, `sampling/createMessage`, or `roots/list` as requests. Instead, a
`tools/call` (or `prompts/get`, `resources/read`) that needs more input returns:

```json
{
  "resultType": "input_required",
  "inputRequests": { "github_login": { "method": "elicitation/create", "params": { ... } } },
  "requestState": "opaque, integrity-protected blob"
}
```

The client gathers answers, then **retries the original request** (new request id) with
`inputResponses` keyed to match, echoing `requestState` verbatim. Key rules:

- All results now carry a required `resultType` (`"complete"` | `"input_required"`); results from
  older servers that omit it are treated as `"complete"`.
- `requestState` is attacker-controlled input on the way back in: servers MUST integrity-protect
  it (HMAC/AEAD) when it influences authz or business logic, SHOULD embed principal + TTL +
  request digest to bound replay.
- Servers MUST NOT send input requests for capabilities the client didn't declare.
- Servers must tolerate the client never retrying.

The elicitation-completion notification and `elicitationId` from 2025-11-25 are removed — the
retry *is* the completion signal.

### 1.3 Tasks: out of core, into an official extension

Tasks move to `io.modelcontextprotocol/tasks`. The redesign:

- Server may return `resultType: "task"` (`CreateTaskResult` with `taskId`, status, `ttlMs`,
  `pollIntervalMs`) on any supported request, **unsolicited**, as long as the client declared the
  extension in its per-request capabilities.
- Client polls **`tasks/get`**; blocking `tasks/result` is gone; `tasks/list` is gone.
- Mid-flight input composes with MRTR: a task in `input_required` surfaces an `inputRequests`
  map; the client answers via **`tasks/update`**.
- Statuses: `working`, `input_required`, `completed`, `failed`, `cancelled` (last three
  terminal). `tasks/cancel` is cooperative.
- Optional push via `notifications/tasks` over `subscriptions/listen`; polling is the default.

### 1.4 Deprecations

- **Roots, Sampling, Logging** are formally Deprecated (12-month window). Suggested migrations:
  directories via tool params/config instead of Roots; call your LLM provider directly instead
  of Sampling; stderr/OpenTelemetry instead of Logging.
- **HTTP+SSE transport** (the 2024-era two-endpoint style) reclassified Deprecated.
- **Dynamic Client Registration (RFC 7591)** deprecated in favor of **Client ID Metadata
  Documents (CIMD)**: the `client_id` *is* an HTTPS URL pointing at a JSON metadata document
  (`client_id`, `client_name`, `redirect_uris`, …). Authorization servers fetch and validate it
  on demand; support is advertised via `client_id_metadata_document_supported` in AS metadata.
  Client priority order: pre-registered → CIMD → DCR fallback → ask the user. CIMD client ids
  are portable across authorization servers; DCR/pre-registered credentials MUST be keyed by
  issuer and never reused across authorization servers.

### 1.5 Smaller but load-bearing

- **`extensions` field** on both capability objects — the negotiation mechanism for MCP Apps,
  tasks, auth extensions.
- **`CacheableResult`**: `tools/list`, `prompts/list`, `resources/list`, `resources/read`,
  `resources/templates/list` MUST return `ttlMs` + `cacheScope` (`public`/`private`).
- **Deterministic tool ordering** SHOULD be used — explicitly to improve LLM prompt cache hits.
- **`Mcp-Method` / `Mcp-Name` request headers** required on Streamable HTTP POSTs (routing and
  observability without body parsing); `x-mcp-header` for tool-parameter-driven custom headers.
- OAuth: `iss` validation per RFC 9207 required when present; `application_type` required in DCR;
  error-code range `-32020`…`-32099` reserved for the spec; resource-not-found is now `-32602`.
- OpenTelemetry `traceparent`/`tracestate`/`baggage` conventions for `_meta`.

### 1.6 UI: MCP Apps is the sanctioned surface

Interactive UI stays an extension (`io.modelcontextprotocol/ui`, the ext-apps repo). The shape:
tools point at a `ui://` resource via `_meta.ui.resourceUri`; hosts preload it, render the HTML
in a sandboxed iframe, and the app talks a `ui/*` JSON-RPC dialect over `postMessage` — it can
call server tools through the host, push context updates, and receive fresh tool results.
Negotiation rides the new `extensions` capability field (e.g. client advertises
`{"io.modelcontextprotocol/ui": {"mimeTypes": ["text/html;profile=mcp-app"]}}`). Graceful
degradation is normative guidance: UI-enhanced tools should still return meaningful text.

## Part 2 — Umwelten impact map

Full inventory as of 2026-07-29, `@modelcontextprotocol/sdk@1.29.0` pinned everywhere (one
outlier: `examples/twitter-mcp` at `^1.27.1`).

| Spec change | Umwelten status | Verdict |
|---|---|---|
| Session removal | Every server already `sessionIdGenerator: undefined` with a fresh `McpServer` per request (`mcp-serve/mcp-handler.ts:131-148`, `habitat/mcp-local-server.ts:112-125`, `habitat/container-server.ts:965-972`) | **Already conformant** — the design bet paid off |
| initialize → `_meta` + `server/discover` | Entirely delegated to SDK 1.29.0; zero `_meta`/`server/discover` in repo code | **SDK bump absorbs it** for modern paths |

| **DCR → CIMD** | We implement DCR on **both sides**: client (`remote.ts:103-112` + forked copy in `examples/mcp-chat/tezlab-mcp.ts`) and authorization server (`mcp-serve/oauth/register.ts`, advertised at `oauth/metadata.ts:23`) | **Biggest real migration** |

| Legacy `2024-11-05` client + stdio/SSE/WebSocket transports | `mcp/client/client.ts:64,258`, `mcp/types/transport.ts`; consumed only by `mcp connect`/`test-tool`/`read-resource` and `mcp/integration/stimulus.ts` | **Delete** — now three revisions stale, declares roots/sampling it can't serve |

Cosmetic debris to sweep in the same pass: `Mcp-Session-Id` still named in a CORS allow-list

and CLAUDE.md's claim that `mcp/server/server.ts` exists (it doesn't — the directory holds only
`client/`, `integration/`, `types/`).

## Part 3 — Best practices, mapped to our stack

### 3.1 Agent interoperability

**Statelessness as the default posture — keep it, and finish it.**
The spec now says what our architecture already assumed: MCP is the stateless tool wire; session
identity lives elsewhere. In our stack "elsewhere" is the A2A layer — `contextId` keys the
habitat session (`a2a-handler.ts:376`), and the per-user JWT `sub` binds the speaker (ADR 0003,
ADR 0005 §9). The new rule "cross-call state = server-minted handles passed as tool arguments"
is exactly the session-handle pattern `src/session-record/` already uses internally. Best
practice: never reintroduce connection-affine state on `/mcp`; when a habitat tool needs
continuity, return a handle in the tool result and accept it as an argument.

**One task idiom across both protocols.**
MCP tasks (`tasks/get` polling, `pollIntervalMs`, cooperative `tasks/cancel`, `input_required`
with `inputRequests`) is a structural sibling of A2A tasks as we built them in ADR 0007
(`configuration.blocking: false`, `tasks/get`, `pollA2ATask` backoff, `tasks/cancel`, sweep and
notify). Best practice: treat ADR 0007's polling contract as the house idiom and implement the
MCP tasks extension as a second carrier of the *same* semantics — a long-running habitat tool
(`agent_ask`, `agent_converse`, provisioning) should be able to surface as an MCP task to an MCP
client and as an A2A task to a peer habitat, backed by the same `FileTaskStore`. That makes the
container-server's `/mcp` a real peer of `/a2a` for delegation instead of a synchronous-only
surface.

**`server/discover` is MCP growing an agent card.**
A mandatory, cacheable, unauthenticated-callable discovery RPC returning identity, versions, and
capabilities is functionally the `/.well-known/agent-card.json` of MCP. Our habitats already
publish A2A agent cards with credential requirements (ADR 0004's `requiredCredentials`,
`credentialMode`). Best practice: when the SDK ships `server/discover`, populate it from the
same source of truth as the agent card so the two discovery surfaces can't drift — name,
version, capabilities, and auth pointers should be one definition rendered twice. This also
slots into the discovery ladder we already publish (OAuth protected-resource metadata + agent
card on habitat hosts).

**MRTR for tool-side interactivity.**
We have never had an elicitation surface; MRTR makes one buildable without breaking our
stateless servers, because the *pattern is designed for exactly our architecture* (no shared
state across instances). Two sides:

- *Server side (mcp-serve + habitat tools):* a tool that needs confirmation or missing
  parameters returns `resultType: "input_required"` with an `ElicitRequest` and an
  HMAC-protected `requestState` (principal + TTL + request digest, per spec). Approval-gated
  habitat actions — deploys, spend, `agent_configure` — are the natural first users.
- *Client side (`RemoteMcpClient` + `mcp chat`):* the tool-call loop must branch on
  `resultType`, render the elicitation (terminal prompt in `mcp chat`; form in web chat), and
  retry with `inputResponses` + echoed `requestState`. Declare the `elicitation` capability only
  once this loop exists — the legacy client's sin of declaring capabilities it can't serve is
  precisely what the new spec's "MUST NOT send undeclared inputRequests" rule exists to punish.

**Kill the legacy stack.**
`mcp/client/client.ts`, `mcp/types/transport.ts` (stdio/old-SSE/WebSocket), and the
`mcp connect`/`test-tool`/`read-resource` trio hardcode `2024-11-05`, hand-roll `initialize`,
and declare roots/sampling with no handlers. Under a spec that has removed the handshake and
deprecated those features, the cheapest correct move is deletion (fold any still-wanted debug UX
into `mcp chat` over `RemoteMcpClient`). Also fold the forked client in
`examples/mcp-chat/tezlab-mcp.ts` back onto `RemoteMcpClient` — every client-side migration
currently has to be done twice.

**Auth: CIMD without breaking the fleet.**
- *Client side:* host a Client ID Metadata Document (a static JSON at a stable HTTPS URL — the
  artifacts service or a habitat host both work) and teach `FileOAuthClientProvider` the spec's
  priority order: pre-registered → CIMD (when `client_id_metadata_document_supported`) → DCR
  fallback. Independently of CIMD, the credential store must be **keyed by issuer**, not by
  server URL — today two scopes or a changed authorization server collide in one
  `~/.umwelten/mcp-auth/<host><path>.json` file, which the new spec explicitly forbids reusing
  across issuers.
- *Server side (mcp-serve is an authorization server):* accept URL-formatted `client_id`s —
  fetch the metadata document, validate `client_id` matches the URL exactly, validate
  `redirect_uri` against the document, cache per HTTP headers — and advertise
  `client_id_metadata_document_supported: true`. Keep `/oauth/register` as the documented DCR
  fallback during the 12-month window. Store impact: `McpServeStore` grows a resolved-CIMD
  cache path alongside DCR client rows. While in there: validate the RFC 8707 `resource`
  parameter we currently capture and ignore, and add RFC 9207 `iss` emission/validation.

**Caching and prompt-cache hygiene.**
Return `ttlMs`/`cacheScope` from list endpoints (per-request tool registration makes this
nearly free — the registrar knows how stable its tool set is) and keep tool ordering
deterministic. The spec's rationale is one we independently care about: stable tool lists are
prompt-cache-friendly, and our own eval data shows tool-calling cost is dominated by context
overhead. This also matters for our *client*: `RemoteMcpClient` snapshots tools once per
connect; with `ttlMs` it can cache correctly across short-lived CLI invocations.

### 3.2 UI experiences

**We bet on mcp-ui early; the extension formalizes the bet.**
ADR 0005 already carries UI resources over both A2A (`DataPart`, output mode `text/html+mcp`)
and MCP (`EmbeddedResource` blocks via `aiResultToMcpContent`, `@mcp-ui/server`
`createUIResource`), and we already depend on `@modelcontextprotocol/ext-apps@0.3.1`
transitively. What changes with 2026-07-28: negotiation becomes explicit. Best practices to
adopt as the extension lands in hosts:

1. **Negotiate, don't assume.** Emit UI resources only when the client's per-request
   `extensions` capability includes `io.modelcontextprotocol/ui` (with a matching mimeType).
   Today we attach `EmbeddedResource` blocks unconditionally; under the new spec the capability
   field finally tells us who can render them.
2. **Text fallback is normative, not politeness.** Every UI-emitting habitat tool must return a
   meaningful text block alongside the resource — the spec's graceful-degradation guidance
   matches ADR 0005's existing text-flattening rule; keep enforcing it.
3. **The per-user speaker binding is our differentiator — keep it on the app path.** ADR 0005 §9
   (UI tool callbacks run as the verified viewing user via JWT `sub` →
   `runWithSpeaker`) is exactly the consent-and-identity story the Apps security model wants
   hosts to have; as we grow a web host for apps (container-server chat), route `ui/*`-initiated
   tool calls through the same binding.
4. **Elicitation is the low-fi UI tier.** Not every interaction needs an iframe app. The spec
   now gives three tiers of tool-side UX: plain text → MRTR elicitation forms → MCP Apps.
   Habitat tools should climb that ladder only as far as the interaction requires; a
   confirmation is an elicitation, not an app.

**CLI/chat surfaces get a concrete to-do list.**
`mcp chat` is currently a pure text client with excellent OAuth UX and no interactivity surface.
Under the new spec its loop needs: `resultType` branching, elicitation rendering (prompt/form),
task-handle handling (`resultType: "task"` → poll with spinner honoring `pollIntervalMs` —
mirroring what `habitat chat` already does for A2A streaming), and `server/discover`-based
capability display on connect (replacing the current "list tools and hope").

### 3.3 Cross-check against house standards (STD-010 / GDE-001)

The Focus AI agent-services standard (`standards` repo: `STD-010-agent-services.md`, extracted
from `GDE-001-a2a-agent.md`) reads like it anticipated this revision:

- **STD-010 §3.2 (one `ToolSpec`, projected to every surface)** — now extends naturally to
  `server/discover`: identity/capabilities/versions should be a third projection of the same
  definition that already yields the AI SDK tool, the MCP registration, and the AgentCard.
- **STD-010 §3.6 (sessions persist to Postgres) + GDE-001 §7 (stateless MCP route,
  `sessionIdGenerator: undefined`)** — precisely the spec's new state model: no protocol
  sessions; durable state server-side, addressed by explicit handles. The GDE-001 `DELETE`
  no-op handler is now removable, as is any lingering session-header handling.
- **STD-010 §3.3 (typed, advertised refusals)** — sharpened by MRTR: "I need more input" is now
  a protocol-level result (`input_required`), so a refusal and an elicitation are formally
  distinct shapes. A tool should never elicit where it means to refuse, or refuse where the
  caller could simply be asked.
- **STD-010 §3.7 (one agent entry point, many surfaces)** — the MCP tasks extension and A2A
  tasks can share one task store behind that single entry point, keeping the "two surfaces, one
  behavior" invariant for long-running work too.
- **GDE-001 §§4.1/5 (MCP-UI resources + AgentCard-advertised media types)** — carries over, with
  the addition that UI emission should now be gated on the client's
  `io.modelcontextprotocol/ui` extension capability rather than emitted unconditionally.

## Part 4 — Adoption sequencing (as decided, 2026-07-29)

The plan below was stress-tested in a grilling session on 2026-07-29; the load-bearing
decisions are recorded as ADR 0012 (one task substrate), ADR 0013 (MRTR state splits by mode),
and ADR 0014 (client identity hosted per product). The adoption goal is **interop-first**:
the target state is `/mcp` as a delegation peer of `/a2a`; pure conformance rides behind the
SDK bump rather than leading.

1. **Wave 1 — hygiene (no behavior change):** SDK bump when 2026-07-28 support ships (align
   `twitter-mcp` to the workspace version); **delete the legacy stack outright** — legacy
   client, stdio/old-SSE/WebSocket transports, and the `mcp connect`/`test-tool`/
   `read-resource` commands (fold surviving debug ergonomics into `mcp chat`); de-fork
   `tezlab-mcp.ts`; sweep `Mcp-Session-Id` CORS mention, DELETE stubs, stale walkthrough body,
   stale CLAUDE.md entry; key the client auth store by issuer.
2. **Wave 2 — interop (the payoff):** MCP tasks extension as a projection over the ADR 0007
   `FileTaskStore` (ADR 0012); MRTR elicitation — shared `requestState` helper in mcp-serve
   for synchronous calls, task-record input for task-mediated operations (ADR 0013);
   `input_required`/`task` result handling + elicitation UX in `RemoteMcpClient` and
   `mcp chat`; `server/discover` and the A2A agent card projected from one source of truth.
3. **Wave 3 — auth:** CIMD on the mcp-serve authorization server (advertise + resolve, DCR
   endpoint retained as fallback through the window); CIMD-first client resolution order with
   the client document hosted per product (ADR 0014); `iss` validation, `resource` binding.
4. **Wave 4 — caching + UI negotiation:** `ttlMs`/`cacheScope` on list results; deterministic
   tool ordering audit; UI resources gated **negotiate-when-possible** — strict capability
   gating for clients that send 2026-07-28 `_meta`, today's unconditional emission for older
   clients, mandatory text fallback in both cases (ADR 0005) — so strictness arrives as
   clients upgrade, with no flag day; wire the web chat host toward the ext-apps AppBridge.

None of this is urgent in the breaking sense — 1.29.0-era servers and clients interoperate
through the deprecation window — but Wave 1 is cheap insurance, and Wave 2 is where the spec
finally pays *us*: it turns `/mcp` into a full peer of `/a2a` for agent delegation, which is
the direction the whole fleet architecture (ADR 0007, 0008) is already pointed.
